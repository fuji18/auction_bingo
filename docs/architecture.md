# 技術仕様書 (Architecture Design Document)

> 本書は「どう作るか」の技術的な骨格を定義する。ゲームルールとデータモデルは `docs/functional-design.md`、要件は `docs/product-requirements.md` を参照する。

## テクノロジースタック

### 言語・ランタイム

| 技術 | バージョン | 備考 |
|------|-----------|------|
| Node.js | v24.x | devcontainer / CI / `engines` で固定 |
| TypeScript | 6.0.x | `strict` + `verbatimModuleSyntax` + `isolatedModules` |
| npm | 11.x | |

**ブラウザ対応**: ビルドターゲットは `es2022`。モダンブラウザの直近2バージョン(Chrome / Safari / Firefox / Edge)を対象とし、iOS Safari を含む。IE および旧 Edge は対象外。

### フレームワーク・ライブラリ

| 技術 | バージョン | 用途 | 選定理由 |
|------|-----------|------|----------|
| Svelte | 5.56.x | UI 描画 | 既存スポーク `kanji_gacha` と同構成。ロジックが `core/` に分離済みで UI 層が薄いため、ボイラープレートの少なさとバンドルの軽さが直接効く。runes による細粒度の反応性で、3盤面の部分更新が素直に書ける |
| Vite | 8.1.x | ビルド / 開発サーバー | 静的サイト出力。`sim/` も同一 TS 設定で動く |

## アーキテクチャパターン

### レイヤー構成

```
┌──────────────────────────────────────┐
│  ui/        Svelte コンポーネント     │ ← 描画とアクション送出のみ
├──────────────────────────────────────┤
│  agents/    意思決定 (CPU)            │ ← PublicView/SecretView のみを見る
├──────────────────────────────────────┤
│  core/      純粋なゲームロジック       │ ← 何にも依存しない
└──────────────────────────────────────┘
      ▲
      │ core/ のみに依存
┌──────────────────────────────────────┐
│  sim/       自動対戦 (CLI)            │
└──────────────────────────────────────┘
```

**この依存方向が本プロダクトの設計の中心であり、唯一妥協してはいけない制約。** P1 のサーバー移行は `core/` を無改変でサーバーへ移送することで成立する。`core/` に UI・DOM・タイマー・I/O が1行でも混入した時点で、その前提が崩れる。

#### `core/` レイヤー

- **責務**: ゲーム状態の生成と遷移、盤面判定、乱数生成。
- **許可される依存**: なし(TypeScript の標準ライブラリのみ)。
- **禁止される操作**:
  - DOM API(`document` / `window` / `localStorage`)へのアクセス
  - `Math.random()` の呼び出し
  - `Date.now()` / `new Date()` の呼び出し
  - `fetch` / ファイル I/O
  - `console` への出力
  - Svelte / Vite への依存
- **副作用を持たない**: `reduce` は入力 state を破壊せず、新しい state と events を返す。

#### `agents/` レイヤー

- **責務**: `PublicView` と `SecretView` からアクションを決定する。
- **許可される依存**: `core/` の型と純粋関数(盤面判定など)。
- **禁止される操作**: `GameState` 全体を引数に取ること。`deck` の中身や他者の `submissions` を参照すること。`core/` レイヤーと同じ副作用の禁止事項がすべて適用される。

#### `ui/` レイヤー

- **責務**: `state` の描画、ユーザー入力のアクションへの変換、`localStorage` への退避、演出。
- **許可される依存**: `core/` / `agents/`。
- **禁止される操作**: **ルール判断の実装**。「この入札は不正か」「誰が落札したか」「ビンゴか」を UI 側で判定してはならない。UI が持ってよいのは「`legalActions` が返した範囲でしか入力させない」という制約表現までとする。

#### `sim/` レイヤー

- **責務**: 自動対戦の実行とKPI集計。Node.js 上で動く。
- **許可される依存**: `core/` / `agents/`。`ui/` に依存してはならない。

### 依存規則の機械的な強制

レビューの目視に頼らず、**ESLint の `no-restricted-imports` と `no-restricted-globals` で違反をエラーにする**。

```javascript
// eslint.config.js に追加する制約(実装チケットで導入)
{
  files: ['src/core/**/*.ts', 'src/agents/**/*.ts'],
  rules: {
    'no-restricted-globals': ['error',
      'window', 'document', 'localStorage', 'fetch', 'console'],
    'no-restricted-properties': ['error',
      { object: 'Math', property: 'random' },
      { object: 'Date', property: 'now' }],
    'no-restricted-imports': ['error', { patterns: ['**/ui/**', '**/sim/**', 'svelte', 'svelte/*'] }],
  },
},
{
  files: ['src/core/**/*.ts'],
  rules: {
    'no-restricted-imports': ['error', { patterns: ['**/ui/**', '**/agents/**', '**/sim/**', 'svelte', 'svelte/*'] }],
  },
},
{
  files: ['src/sim/**/*.ts'],
  rules: {
    'no-restricted-imports': ['error', { patterns: ['**/ui/**', 'svelte', 'svelte/*'] }],
  },
}
```

`new Date()` は `no-restricted-syntax` で、`sim/` からの `ui/` 参照は同様の `no-restricted-imports` で塞ぐ。**この設定自体を最初の実装チケットの成果物に含める。** 後から入れると既存コードの違反を潰す作業が発生する。

## データ永続化戦略

### ストレージ方式

| データ種別 | ストレージ | フォーマット | 理由 |
|-----------|----------|-------------|------|
| 進行中ゲーム | `localStorage` | JSON (`{ version, seed, actions[] }`) | リロードで進行を失わないため。state 全体ではなく操作列を保存することで、データ量が小さく、ルール変更に対する互換性の判断も `version` 1つで済む |
| 直近の試合結果 | `localStorage` | JSON | 「もう一度」からのリプレイ再生に使う |
| バランス定数 | ソースコード内の定数 | TypeScript | 実行時に変更する要件がない。`sim/` からは CLI 引数で上書きできるようにする |
| ユーザーアカウント / 戦績 | **持たない** | — | スコープ外(PRD) |

**保存キーは `auction-bingo:` を接頭辞とする。** 同一ドメイン配下に他のスポークが同居する可能性は低いが、衝突を構造的に避ける。

### 復元と破棄

```
復元: reduce(createGame(config, seed), actions)  で state を再構築する
破棄条件:
  - version が現在のスキーマと一致しない
  - JSON のパースに失敗した
  - 復元中に reduce が不正アクションとして拒否した
```

破棄時はセーブを削除して新規ゲームを開始し、ユーザーには「保存データを読み込めませんでした。新しいゲームを開始します」と表示する(UI 文言の正典は `docs/functional-design.md` の「エラーハンドリング」表とする)。**部分的な復旧は試みない。** 中途半端に壊れた state で遊ばせるより、作り直させるほうが安全であり、実装も単純になる。

### バックアップ戦略

**行わない。** 保存対象は進行中の1ゲームのみで、失われても再プレイのコストが10分程度であり、世代管理の複雑さに見合わない。

## パフォーマンス要件

### レスポンスタイム

| 操作 | 目標時間 | 測定環境 |
|------|---------|---------|
| 初回ロード(操作可能になるまで) | 3秒以内 | 4G 回線相当・キャッシュなし・中位のスマートフォン |
| `reduce` 1ターン分の計算 | 10ms 以内(**UI 上の上限**) | 開発機 |
| 提出から解決結果の表示まで | 500ms 以内 | 実機。演出時間を含む |
| 盤面のマーク反映 | 16ms 以内(1フレーム) | 実機 |
| 自動対戦 1万戦 | 5分以内 | 開発機・単一プロセス |

**「1ターン 10ms 以内」は UI 上の体感を守るための上限であり、実測目標ではない。** 実質的な性能要件はシミュレーション側から決まる。1万戦を5分以内(1ゲーム 30ms 以内)、期待ターン数が約18であることから逆算すると、**1ターンあたり 1.7ms 以内**が実際に満たすべき水準になる。UI 側の 10ms はここに約6倍の余裕を見た値であり、両者は矛盾しない。

### リソース使用量

| リソース | 上限 | 理由 |
|---------|------|------|
| 配信バンドル | gzip 200KB 以内 | 3秒以内のロード目標から逆算。Svelte 5 の骨格のみで gzip 約9KB のため、十分な余裕がある |
| ヒープ | 50MB 以内 | 中位のスマートフォンで安定動作させるため。state は数KB 規模で、支配的なのは Svelte のランタイムと DOM |
| `localStorage` | 100KB 以内 | 操作列は1ゲーム最大75アクション程度で、実測は数KB に収まる見込み |

### 最適化方針

- **ラインの添字を定数化**する。12本のラインを毎回構築しない。
- **`sim/` は UI を経由しない。** イベントの記録も集計に不要な分は抑制できるようにする。
- **計算と演出を分離する。** `reduce` を先に完了させ、events を順に再生することで演出時間が計算をブロックしない。
- **早すぎる最適化はしない。** 上記の目標時間を割ったことを計測で確認してから着手する。

## セキュリティアーキテクチャ

### 脅威モデル

P0 は**クライアント完結の一人用ゲーム**であり、守るべき対戦相手も秘密情報も存在しない。したがって:

- **クライアント側の state 改竄は脅威として扱わない。** 自分のゲームを自分で壊すだけであり、対策コストに見合わない。
- **認証情報・個人情報を一切持たない。** 保存するのは seed と操作列のみ。

### データ保護

- **暗号化**: 不要(秘匿すべきデータを持たないため)。
- **通信**: Cloudflare Pages 上で HTTPS 配信する。
- **外部スクリプト**: 読み込まない。解析は Cloudflare Web Analytics のみを使い、Cookie を用いず個人を特定しない。
- **機密情報管理**: リポジトリにシークレットを置かない。pre-commit と CI で secretlint を実行する。

### 入力検証

- **すべての検証を `core/` 側で行う。** UI 側のガードは体験のためのものであり、信頼の境界ではない。
- `reduce` は不正なアクション(コイン超過・負の入札・フェーズ不一致)を**拒否して state を変更しない**。例外を投げず、events にも記録しない。
- エラー表示に内部状態を含めない。

### P1(サーバー化)以降の制約

サーバー権威型に移行した時点で脅威モデルが変わり、以下が**必須の制約**になる。

- **クライアントへ送信してはならない情報**: `deck` の中身、開札前の他者の `submissions`、他者が購入したスキル、他者の `visionPeek`。
- この境界は `PublicView` 型と完全に一致する。**`PublicView` をシリアライズしたものだけを送る**という実装規約により、境界を型で担保する。
- フェイズごとに制限時間を設け、時間切れ時のデフォルト行動(入札0・スキルなし・パス)を `core/` 側に定義する。

## スケーラビリティ設計

### 負荷特性

P0 は**サーバーを持たない静的サイト**であり、同時接続数は Cloudflare Pages の CDN 配信能力に依存する。アプリケーション側のスケーラビリティ課題は存在しない。

### データ増加への対応

想定データ量は「進行中ゲーム1件」であり、増加しない。アーカイブ戦略は不要。

### 機能拡張性

拡張は以下の3方向を想定し、それぞれ拡張点を設計時点で確保する。

| 拡張方向 | 拡張点 | 現時点で確保すること |
|---|---|---|
| **CPU の追加**(P2) | `Agent` インターフェース | レオ / サラを最初から同一インターフェースで実装し、特別扱いしない |
| **オンライン対戦**(P1→P2) | `Agent` インターフェース + `core/` の可搬性 | リモートプレイヤーを `Agent` の別実装として差し込めること。空席の CPU 埋めが同じ仕組みで実現できること |
| **ルール変更・バランス調整** | `BalanceConfig` | すべての調整可能な数値を単一の設定オブジェクトに集約し、コード中に数値リテラルを置かない |

### P1 サーバー移行の想定経路

**現時点では決定せず、経路の存在だけを確認しておく。**

- `core/` はランタイム非依存のため、Cloudflare Workers / Durable Objects 上でそのまま動く。
- **ルーム = アクター**という構造が Durable Objects の単位と一致するため、配信基盤(Cloudflare Pages)と同一プラットフォーム上で完結できる。
- 必要になる要素は WebSocket による常時接続、フェイズごとの制限時間、再接続復帰、3人分のマッチメイキング。
- ターン制で state が極小のため、リアルタイムゲームに必要なラグ補償・補間は不要。

## テスト戦略

### ユニットテスト

- **フレームワーク**: Vitest 4
- **対象**: `core/` の全モジュール(`rng` / `board` / `reduce` / `config`)と `agents/` の判断関数。
- **カバレッジ目標**: `core/` は **90% 以上**。ルールの実装そのものであり、ここのバグは全プレイに影響する。`ui/` には数値目標を課さない。
- **方針**: `core/` は純粋関数のためモック不要。入力と期待値の表で網羅する。境界値(`target = 1` / `40`、コイン上限、入札 0、山札の残量)を必ず含める。

### 統合テスト

- **方法**: シードと操作列からゲームを最後まで進め、state と events を検証する。
- **対象**:
  - **決定性**: 同一 `(seed, actions[])` から同一の `state` と `events` が再現される。
  - **コイン保存則**: 全プレイヤーのコイン + 銀行回収額 + 上限超過による消滅分 = 初期総額 + 総収入。
  - **セーブ/復元**: `seed + actions[]` からの復元結果が中断前の state と完全一致する。
  - **情報遮断**: `PublicView` に `deck` の中身と他者の `submissions` が含まれないこと。

### シミュレーションテスト

PRD のプライマリー KPI 7項目を `sim/` で計測する。**CI では実行せず、開発者が明示的に実行する。** バランス調整は継続的な作業であり、閾値割れで CI を赤にすると本来の品質ゲートが機能しなくなる。

### E2Eテスト

P0 のスコープでは導入しない。UI 実装フェーズで必要性が生じた時点で Playwright を追加する(既存スポーク `kanji_gacha` に前例がある)。

### CI で実行するもの

`npm run lint` / `npm run typecheck` / `npm test` / `npm run format:check` / `npm run build` / `npx secretlint` / `npm audit --audit-level=high`(非ブロッキング)/ ハーネス整合検証(フックの実行権限と `settings.json` の構文)。

`main` / `develop` への push と、**対象ブランチを問わずすべての PR** で実行する。Claude による自動コードレビュー(`claude-code-review.yml`)はこれとは別で、`main` 向け PR のオープン時と ready_for_review 時のみ起動する。

## 技術的制約

### 環境要件

- **開発環境**: devcontainer(Node.js v24 / npm 11)。
- **実行環境**: モダンブラウザ直近2バージョン。JavaScript 必須。
- **必要な外部依存**: なし。オフラインでも動作する(P0 は通信を行わない)。
- **画面**: 幅 375px の縦画面で破綻しないこと。

### パフォーマンス制約

- 1万戦のシミュレーションを単一プロセスで5分以内に完走する必要があるため、1ゲームあたり 30ms 以内で処理できること。`reduce` の実装で不要なディープコピーを避ける。
- 中位のスマートフォンを基準とする。開発機の性能で判断しない。

### セキュリティ制約

- リポジトリは public。**シークレットを一切含めない。**
- 外部スクリプト・外部フォント・外部画像を読み込まない。
- P1 以降、`PublicView` に含まれない情報をクライアントへ送信しない。

### ハブ&スポーク構成に由来する制約

- 本リポジトリは `fujioha_platform`(Astro のハブ)に対する**スポーク**であり、独立リポジトリ・独自サブドメイン(`auction-bingo.fujioha.com` を想定)で完結する。
- 共有パッケージ `@fujioha/ui` は Astro 専用のため**使わない**。ハブとは URL でのみ繋がる疎結合を維持する。
- 公開時にハブ側へゲーム登録(`apps/game/src/content/games/auction-bingo.json`)が必要。`icon` の enum にビンゴ向けの値が無いため schema 拡張も要る。**これはハブ側リポジトリの作業であり、本プロジェクトのスコープ外**(PRD)。

## 依存関係管理

| ライブラリ | 用途 | バージョン管理方針 |
|-----------|------|-------------------|
| svelte | UI | `^5.56.7`(マイナー追従) |
| vite / @sveltejs/vite-plugin-svelte | ビルド | `^` 指定。メジャー更新は手動で検証する |
| typescript | 型 | `~6.0.0`(**パッチのみ**。マイナー更新でも型エラーの出方が変わるため) |
| vitest / eslint / prettier 等 | 開発ツール | `^` 指定 |

- **更新は Dependabot に委ねる。** `.github/dependabot.yml` が npm と devcontainers を対象に設定済み。
- **ランタイム依存を増やすときは判断を残す。** 決定性を壊す可能性(内部での `Math.random()` / `Date.now()` の使用)を確認し、`core/` から使う場合は特に慎重に判断する。原則として `core/` にランタイム依存を追加しない。
- `npm audit --audit-level=high` を CI で実行する(非ブロッキング)。
