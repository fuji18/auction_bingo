## プロダクトビジョン

**一言で言うと**: 運任せのビンゴを「オークション」「有料の確率操作」「読めないCPU」で再構築した、**確率を金で買う**対戦型 Web ボードゲーム。

- **「確率を飼い慣らす」体験**: 数字が出るのを祈るのではなく、コインを投じて「欲しい数字、あるいはそれに近い数字」を能動的に引き寄せる。
- **二重のコスト構造**: 限られたコインを、**オークション(落札する確率)**に使うか、**スキル(落札したときの選択肢)**に使うかで毎ターン悩む。
- **納得できるフェアネス**: CPU の内部ロジックは非公開だが、**傾向は常に開示**され、**試合後リプレイで手の内を完全開示**する。プレイするたびに読みが上達する。

---

## 解決したい課題

1. 従来のビンゴは完全な運ゲーで、プレイヤーの意思決定が結果にほとんど影響しない（受動的な体験）。
2. 対戦ゲームの CPU は挙動がブラックボックスで、負けたときに「理不尽」「イカサマでは」という不信感を生む。
3. 心理戦・読み合いのあるボードゲームは、対面で人を集める必要がありプレイの敷居が高い。

---

## ターゲットユーザー

### ペルソナ

- 20〜40代のボードゲーム／パズル好き。運要素だけのゲームには物足りなさを感じている。
- 短時間（1プレイ 10〜15 分）で、読み合いと最適化の手応えがある対戦を求めている。
- 相手の傾向を読み、リソース配分を最適化していく過程が好き。

## 主要機能の候補

### P0 (MVPで絶対必要)

#### 1. ビンゴカード

- 数字プールは **1〜40**。列ごとに範囲を区切る。

  | 列 | B | I | N | G | O |
  |---|---|---|---|---|---|
  | 範囲 | 1-8 | 9-16 | 17-24 | 25-32 | 33-40 |

- 各列の8個から5個を選んで配置した $5 \times 5$ の盤面。**盤面命中率は 5/8 = 62.5%**。
- 全プレイヤーの盤面は常時公開。リーチ状況も公開する。

#### 2. コイン経済

- 初期 **15枚**、上限 **30枚**（超過分は消滅）、毎ターン開始時に全員へ **1枚**支給。

#### 3. ターン進行（2ステップ）

**ステップ1: 同時提出（スキル + 入札を1回で決定）**

ターゲット番号 $T$ が公開された後、全員が同一画面で以下をまとめて提出する。

```
手持ち 16 枚
├ スキル: [偏向 4] [予知 5] [強奪 6] [なし]
└ 入札額: [ 8 ] 枚
─────────────────
残り 4 枚   ※スキル代は予約され、入札には使えない
```

| スキル | コスト | 効果 |
|---|---|---|
| 偏向 Shift | 4 | 落札時の選択肢を $\{T-1, T, T+1\}$ に拡張 |
| 予知 Vision | 5 | 山札の上から**3枚を見て、1枚を選んで一番上に戻す**。残り2枚は山札に戻してシャッフルする（＝**次ターンの $T$ を3択から指定できる**） |
| 強奪 Greed | 6 | 落札時の選択肢を $\{T-2 \ldots T+2\}$ に拡張 |

- **スキル代は「予約」制**: 提出時にコインが予約（ロック）され、**予約分は入札に使えない**。偏向・強奪は**落札した場合のみ徴収**され、落札できなければ返却される。二重のコスト構造は予約によって維持しつつ、「払ったのに落札できず丸損」を防ぐ。
- **予知のみ即時徴収**: 落札の有無にかかわらず効果が発生するため。
- **スキルの競合**: 同一ターンに複数人が**予知**を選択した場合、**優先権トークンに最も近い者のみが成功**し、他の購入者にはコストを**全額返金**する。山札という共有資源を同時に操作できないための処理。偏向・強奪は個人の権利購入なので競合しない。
- $T \pm n$ が 1 未満・40 超になる場合は**その候補を除外**する（クランプも循環もしない）。

**ステップ2: 解決（この順序で処理する）**

1. **予知を解決**する（山札操作）。今ターンの $T$ には影響しない。
2. **開札**し、落札者を決定する。落札者は最高額の単独入札者。同額1位が出た場合は**優先権トークン**の保持者に近い者が落札する（トークンは毎ターン時計回りに回転し、常時公開）。
3. **落札者が数字を選ぶ**。購入した範囲から1つ選ぶか、**何も選ばない（パス）ことを選べる**。
4. 選ばれた数字を、**盤面に持っている全員がマークする**（パスの場合は誰もマークしない）。
5. **精算**する。落札者のみが入札額を支払う（敗者は支払わない）。各敗者の受取額は $\lfloor 入札額 \div 4 \rfloor$、残りはすべて銀行が回収する。
6. 縦・横・斜めの**ビンゴを判定**する。達成者がいればゲーム終了。

**パスを認める理由**: 盤面命中率が 62.5% のため、スキル未購入で落札すると約37.5%のターンで「自分が持たない数字を強制的に選ばされ、他者だけがマークする」という自傷が発生する。パスを認めることで、これが「$T$ を持たないが相手にも取らせたくない」ターンの**妨害手段**に変わる。

#### 4. 勝利条件

- **20ターン以内**に1ライン以上のビンゴを最速で達成した者の勝ち。
- 誰も達成しなかった場合は **最長リーチ数 → 総マーク数 → コイン残**の順で比較する。

#### 5. CPU（オートマタ 2体）

- **ロジック（数式・閾値）は非公開**。ただし以下でフェアネスを担保する。
  - **傾向の常時開示**: 「レオ = 序盤に積む猪突型」「サラ = 追随して差し込む型」
  - **テル**: 提出前に状態を1語表示（「レオ: 強気」「サラ: 様子見」）。確率的なヒントであり確定情報ではない。
  - **試合後リプレイ**: 全ターンの入札額・スキル・判断を完全開示する。
  - **非公開情報を CPU は参照しない**ことを UI 上で明言する。
- CPU は**リモートプレイヤーと同一のインターフェース**で実装する（後述）。

#### 6. UI

盤面3枚・手持ちコイン・ターゲット番号・優先権トークン位置・CPUのテル・リーチ状況・ログ・試合後リプレイ。

#### 7. バランス検証基盤 ★実装必須

- **バランス定数をすべて設定ファイルに外出し**（分配率・コイン上限・初期値・スキル価格・ターン数・数字プール）。
- **自動対戦シミュレーション**（シード固定・1万戦規模）で以下を計測する。
  - ビンゴ達成率 / 平均達成ターン
  - **スキル使用率**（目標 40〜60%。低すぎるならスキルがまた死んでいる）
  - **落札回数と勝率の相関** ★最重要。相関が弱ければ、オークションがゲームの中心になっていない赤信号
  - **序盤に貯め込み、終盤のみ入札する戦略の有効性**（「貯め込みスナイプ」の別経路での再発）
  - パス率、および落札者のパス選択が勝率に与える影響

**懸念と対策候補**（紙上トレースで判明、シミュレーションで判断する）

- マークは落札しなくても発生するため、落札の追加価値は「数字を1つ操舵できること」だけ。リーチ前の序盤はこの価値がほぼゼロで、**序盤は全員が貯め込む**のが最適になりうる。
- まず**コイン上限30がブレーキとして機能するか**を測る。不足する場合の対策候補は **落札者ボーナス**（落札者は選んだ数字を、盤面に無くてもフリーマークできる）。序盤から落札価値が立ち上がり、上記の「自傷」問題も同時に緩和されるが、ゲームが速くなりすぎないか要検証。

### P1 (重要だけど後回しでもいい)

- **サーバー権威型への移行**（オンライン対戦の土台。ゲームロジックをそのままサーバーへ移送）。
- 試合後リプレイの共有・振り返り強化。

### P2 (あったら嬉しい)

- **オンライン人間対戦**（マッチメイキング、空席は CPU で埋める）。
- **リアクションスキル**: 開札時にコインを払って割り込む要素。例:【関税】(落札者の支払いを +2)、【保険】(落札失敗時に入札額の半分が戻る)。
- CPU キャラクターの追加。

## 技術的な検討事項

- Web アプリケーション。テンプレート既定の Node.js v24 / TypeScript 6.x を想定。UI フレームワークは未定。
- **P0 はローカル完結**で作り、バランスを固め切ってからサーバー化する（ルール変更のたびに二重メンテになるのを避ける）。

### オンライン化を前提とした必須の設計制約 ★P0から遵守

1. **ゲームロジックを純粋なリデューサとして実装する**
   `reduce(state, actions[]) -> { state, events[] }`。UI・タイマー・乱数に依存させない。これがそのままサーバーで動く。
2. **乱数は state 内の seed から生成する**（`Math.random()` の直呼び禁止）。サーバー移行・リプレイ・シミュレーションが同じ仕組みで実現できる。
3. **CPU をリモートプレイヤーと同一インターフェースで実装する**
   `Agent: (公開情報, 自分の秘密情報) -> Action`。オンライン化は Agent の実装差し替えで済み、CPU による空席埋めも同時に手に入る。

### オンライン化で判明している制約

- **クライアント完結では成立しない**。秘密入札は権威あるサーバーが必須（通信を覗けば相手の入札が見える／後出しできる）。山札もクライアントに置けない（予知が成立しない）。
- ターン制で状態が極小のため、リアルタイムゲームより実装は容易。ラグ補償・補間は不要。
- **必要になる要素**: WebSocket などの常時接続、フェイズごとの制限時間と時間切れ時のデフォルト行動（入札0・スキル無し）、再接続復帰、3人分のマッチメイキング。
- 対戦人数は **3人固定**（プレイヤー1 + CPU2）。オンライン時も空席を CPU で埋めることで 3人固定のまま成立させ、人数可変対応を不要にする。
- **クライアントに送ってはいけない情報**: 山札、開札前の他者の入札、他者が購入したスキル、予知の結果（購入者のみ）。

## 非機能要件(とりあえず)

- 1プレイ 10〜15 分。20ターン × 1回の提出でテンポよく進む。
- 乱数はシード指定で**再現可能**にし、バランス検証・リプレイ・デバッグを可能にする。
- CPU の判断根拠が、傾向・テル・試合後リプレイを通じて必ず事後検証できること。
- ルール上の全処理（分配の端数、上限超過、優先権トークン、範囲外の候補除外）が決定的であること。

---

## 成功指標(とりあえず)

- **ユーザー視点**: 「運ではなく自分の配分判断で勝った／負けた」と感じられる。2戦目以降、CPU の傾向を読んで勝率が上がる実感がある。
- **プロダクト視点**: 支配的戦略が存在しない。シミュレーションでスキル使用率 40〜60%、ビンゴ達成率が十分高いことを確認できる。

## まだ決めてないこと

- UI フレームワーク（React / Svelte / Vanilla TS 等）と状態管理の方針。
- 予知で見た数字の UI 上の保持・表示方法（自分のみ、次ターンまで保持）。
- **予知（5コイン）の強さが妥当か**。次ターンの $T$ を指定できるため、オークションに勝たなくてもマークを狙える＝ゲームの中心ゲートを迂回できる。偏向4 / 予知5 / 強奪6 の価格差はシミュレーションで検証する。
- 予知の競合を「トークンで解決＋返金」にしたことで読み合いの層が1つ減っている。相殺（コスト没収）に戻す案も残す。
- ビジュアルデザイン・キャラクター表現の方向性。
- CPU の傾向表示・テルの具体的な文言設計。

## 改訂履歴

### Ver 3.2（紙上トレースで発見した欠陥の修正）

3人・4ターンの手動トレースを実施して発見した問題への対応。

| 項目 | Ver 3.1 | Ver 3.2 | 理由 |
|---|---|---|---|
| 落札者の選択 | 範囲から1つ**必ず**選ぶ | **パスを選べる** | 盤面命中率62.5%のため、スキル未購入だと約37.5%のターンで「自分が持たない数字を強制選択させられ、他者だけがマークする」自傷が発生していた |
| スキル代 | 提出時に徴収 | **予約制。偏向・強奪は落札時のみ徴収** | 落札できないとコストが丸損になり、指摘1で解消したはずの「落札ゲート依存」が偏向・強奪に残っていた。予約により二重コスト構造は維持される |
| 分配額 | 「50%を敗者へ均等分配、端数は銀行」 | **各敗者 $\lfloor 入札額 \div 4 \rfloor$、残りは銀行** | 毎ターン端数が発生し、プレイヤーが受取額を暗算できなかった |
| 解決順序 | 未定義 | **予知 → 開札 → 選択 → マーク → 精算 → 判定** | 予知が今ターンの $T$ に影響しないことを明示する必要があった |
| 検証項目 | 3項目 | **落札回数と勝率の相関、貯め込み戦略の有効性、パス率を追加** | 「マークは落札しなくても発生する」ため、オークションがゲームの中心から外れている懸念が判明した |

### Ver 3.1（予知の再設計）

| 項目 | Ver 3.0 | Ver 3.1 | 理由 |
|---|---|---|---|
| 予知 | 2 / 次の1枚を見る + 底に送れる | **5 / 3枚を見て1枚を上に戻し、残り2枚はシャッフルして山札へ** | 「見るだけ」は受動的でコンセプト（確率を飼い慣らす）に対して弱い。**次ターンの $T$ を3択から指定する**能動的な選別に変更 |
| 予知の価格 | 2 | **5** | 全員がマークする仕様のため、$T$ を指定できれば**オークションに勝たずにマークできる**。ゲームの中心ゲートを迂回する効果であり最も高価であるべき |
| 予知の競合 | 相殺（コスト没収） | **優先権トークン保持者が成功、他は返金** | 予知が最適購入になり全員が買う → 毎ターン相殺 → 予知が実質存在しなくなる退化を防ぐ |
| 底に送る | あり | **廃止**（残り2枚はシャッフルで山札に戻る） | 数字の実質削除は妨害として一方的すぎる。シャッフル戻しなら再出現の可能性が残る |

### Ver 3.0（Ver 2.3 からの変更点と理由）

| 項目 | Ver 2.3 | Ver 3.0 | 理由 |
|---|---|---|---|
| 数字プール | 1〜25（全カード網羅） | **1〜40、列ごとに8個から5個** | 全カードが全数字を持つとカード運も「Tが無い」緊張も存在しない |
| マーク | 落札者のみ | **落札者が数字を決定、持つ全員がマーク** | 2/3のターンが手待ち。かつ20ターンで最大20マークではライン完成が数学的にほぼ不可能 |
| 落札の基本権利 | $\{T-1,T,T+1\}$ が無料 | **$\{T\}$ のみ。$\pm$ はスキル購入** | コンセプトの核心「リソースを投入して確率をねじ曲げる」が無料で配られていた |
| 偏向 | 5 / T をずらす | **4 / 選択肢を $T\pm1$ に拡張** | 旧仕様は選択肢を増やさず1対1で交換するだけ（$T{-}1$ を失い $T{+}2$ を得る）で価値がほぼ無かった |
| 強奪 | 7 / $T\pm2$ | **6 / $T\pm2$ に拡張** | 7枚は落札1回分の予算と同額。3択→5択がその対価に見合わず数学的に支配されていた |
| 予知 | 3 / 次を見る | **2 / 次を見る + 底に送れる** | 落札できないと価値が出ず、かつ引き切り山札では終盤に無料のカウンティングへ価値が減衰していた |
| 入札分配 | 敗者に100%分配 | **50%分配 / 50%銀行回収** | 分配は移転でありシンクではない。実効シンクが無く全員がコイン上限に張り付いていた |
| コイン上限 | 20 | **30** | 実効シンクができたため、上限を締め付け役から降ろす |
| 同点 | 全額没収の重い罰則 | **優先権トークンで決着（同点ルール廃止）** | 隠匿入札で事故として頻発する上、最も安く降りた者が最大の利益を得る逆インセンティブだった |
| フェイズ | スキル宣言 → 入札 → 判定 | **同時提出 → 判定** | 二重コストが1つの配分決定として可視化され、オンライン時の同期点も半減する |
| バッティング | 全スキル対象 | **予知のみ対象** | 共有資源（山札）を操作するスキルにのみ適用するのが筋。個人の権利購入を相殺するのは不自然 |
| CPU | ロジック完全公開 | **傾向のみ公開 / 試合後リプレイで全開示** | 完全公開だと全員の入札額が事前に判明し、秘密オークションが単なる価格表に退化していた |
| タイムアップ | 未定義 | **最長リーチ → 総マーク → コイン残** | 決着ルールが存在しなかった |
