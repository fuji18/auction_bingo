# プロダクト要求定義書 (Product Requirements Document)

> 元となるアイデアと、そこに至る設計判断の経緯は `docs/ideas/initial-requirements.md`(Ver 3.3)を参照する。
> 本書は「何を作るか」を定義する北極星であり、頻繁には更新しない。

## プロダクト概要

### 名称

**オークション・ビンゴ (AUCTION BINGO)** - 確率を金で買う対戦型ボードゲーム

### プロダクトコンセプト

- **確率を飼い慣らす**: 数字が出るのを祈るのではなく、コインを投じて「欲しい数字、あるいはそれに近い数字」を能動的に引き寄せる。ビンゴから受動性を取り除く。
- **二重のコスト構造**: 限られたコインを、**オークション(落札する確率)** に使うか、**スキル(落札したときの選択肢の広さ)** に使うかで毎ターン悩ませる。どちらか一方に寄せる支配的戦略を作らない。
- **納得できるフェアネス**: CPU の内部ロジックは非公開だが、**傾向は常時開示**し、**試合後リプレイで手の内を完全開示**する。負けたときに「理不尽」ではなく「読み違えた」と感じさせる。

### プロダクトビジョン

ビンゴは本来、プレイヤーの意思決定が結果にほとんど影響しない完全な運ゲームである。本プロダクトは、そこに「オークション」「有料の確率操作」「読めない対戦相手」を持ち込むことで、同じ盤面から**意思決定のゲーム**を再構築する。

プレイヤーは毎ターン、限られたコインをどう割り振るかという1つの決定だけを下す。しかしその決定は、落札できるか・落札したとき何を選べるか・相手に何を渡すかという複数の結果に同時に効く。10〜15分の1プレイの中で、プレイヤーは「運が良かった」ではなく「配分を間違えた」と語るようになる。

CPU のロジックは隠すが、判断の痕跡は必ず事後に検証できる。プレイするたびに相手の癖が読めるようになり、勝率が上がる実感が得られる——それが本プロダクトの提供する体験である。

### 目的

- ビンゴという誰もが知るルールを土台に、学習コストを上げずに戦略性を持ち込む。
- 短時間(10〜15分)で完結し、繰り返し遊ぶほど上達を実感できる対戦体験を提供する。
- 将来のオンライン人間対戦を見据え、ゲームロジックを UI・通信から分離した形で実装する。

## ターゲットユーザー

### プライマリーペルソナ: 佐藤健一(32歳、Webエンジニア)

- **基本属性**: 都内在住、既婚、平日夜と週末に1〜2時間の自由時間がある。
- **技術・嗜好**: ボードゲームカフェに月1回程度通う。『カタン』『枯山水』など、リソース配分と読み合いのあるゲームを好む。スマートフォンのカジュアルゲームは「作業感がある」と感じてすぐ辞める。
- **現在の課題**:
  - 対面のボードゲームは人を集める必要があり、遊びたいときに遊べない。
  - 手軽に遊べるオンラインのボードゲームは、CPU の挙動がブラックボックスで、負けたときに「イカサマでは」という不信感が残る。
  - 運要素の強いゲームは、勝っても負けても自分の判断が結果に効いた実感がない。
- **期待する解決策**: ブラウザを開いてすぐ始められ、10分で終わり、負けたときに自分の判断のどこが悪かったか分かる対戦ゲーム。
- **典型的なワークフロー**: 平日の帰宅後、スマートフォンまたは PC のブラウザで1〜2戦。試合後リプレイで CPU の入札額を確認し、「次はここで降りる」と考えて再戦する。

### セカンダリーペルソナ: 山田美咲(26歳、デザイナー)

- **基本属性**: 都内在住、一人暮らし。通勤電車と就寝前がスマートフォンを触る時間。
- **技術・嗜好**: ゲームは基本的にスマートフォンのブラウザで遊ぶ。アプリのインストールは面倒で避ける。ボードゲーム経験は少ないが、ビンゴのルールは知っている。
- **現在の課題**: ルール説明が長いゲームは始める前に離脱する。チュートリアルを読まされる時点で興味を失う。
- **期待する解決策**: 「ビンゴ」という既知の枠組みのおかげで、初回でも説明なしに何をすればいいか分かること。
- **典型的なワークフロー**: SNS やポータルサイトからリンクを踏んで流入し、説明を読まずにいきなり1戦目を始める。片手・縦画面で操作し、面白ければブックマークして後日また開く。

## 成功指標(KPI)

### プライマリーKPI(プロダクト品質 — シミュレーションで測定)

`src/sim/` の自動対戦シミュレーション(シード固定・1万戦規模)で測定する。**実装完了の判定基準であり、最初のチケットの成果物**。

**既定の計測相手**: プライマリー KPI は「実際の対戦(レオ・サラ + 能動的な第三席)」を代表させるため、既定で `leo,sara,allIn`(第三席=全力入札の攻め型)で測る(`npm run sim` の既定値)。非入札の貯め込み(hoarder)を第三席に置くと、入札を伴う指標(スキル使用率・落札×勝率相関)が構造的に歪む(hoarder は常時 bid 0・スキル非購入のため)。貯め込み・全力入札・スキル不買の各戦略は「支配的戦略の不在」のクロスチェックとして別途回す。

| 指標 | 目標値 | 判断の意味 |
|---|---|---|
| ビンゴ発生率 | **95% 以上** | タイムアップ決着が多発していないか(Ver 3.3 の盤面試算では 97.3%) |
| スキル使用率 | **40〜60%** | 低すぎればスキルが死んでいる。高すぎれば購入が事実上の必須手順になっている |
| 支配的戦略の不在(オークションの中心性) | 単一戦略の勝率が **50% 未満**、かつ**非入札戦略(貯め込み)が均等分 33% を明確に下回る** | 「常に貯め込む」「常に最大入札」等が最適にならないこと。**非入札が勝てない=オークションがゲームの中心である**ことをここで担保する(旧「落札回数と勝率の相関」の意図を統合) |
| 平均決着ターン | **16〜20ターン** | 短すぎれば読み合いが成立せず、長すぎればプレイ時間の要件を割る |
| 終盤(残り5ターン)のスキル選択比率 | **単一スキルが 70% を超えないこと** | 予知はオークションを迂回でき、競合しても全額返金でノーリスクなため、終盤に一極集中する懸念がある |
| パス率 | **1〜15%** | 0% ならパスが死に選択肢。高すぎれば落札しても選ぶ価値のある数字が無いということ |

**参考指標(ゲート外)**: **落札回数と勝率のピアソン相関 r** は当初「オークションの中心性」の主指標(r ≥ 0.3)としていたが、シミュレーションにより第三席の攻撃性で符号が反転する脆い指標だと判明した(貯め込み相手 +0.30 / 全力入札相手 −0.20)。過剰入札は落札を量産しても勝てない=「金だけでは勝てない」設計意図の表れであり、中心性は上表「支配的戦略の不在」に統合した。相関は `sim` 出力に参考値(INFO)として残す。

**測定期限**: P0 実装完了時点。上記を満たすまでバランス定数を調整し、満たせない場合は `docs/ideas/initial-requirements.md` に記録済みの対策候補(落札者ボーナス等)を適用する。

> **KPI 達成状況(2026-07-23 時点・#29 バランス調整後)**
> issue #9 構築時点は達成1項目のみだったが、バランス調整(スキルコスト引き下げ・CPU のスキル購入ロジック見直し)と計測相手・指標定義の見直しで、既定計測 `leo,sara,allIn`(seed=1・1万戦)で**ゲート6項目すべて達成**(相関は参考指標化)。
>
> | 指標 | 目標 | #9 時点(旧計測 hoarder) | 現在(leo,sara,allIn) |
> |---|---|---|---|
> | ビンゴ発生率 | 95% 以上 | 93.6% | **97.2%** ✅ |
> | スキル使用率 | 40〜60% | 15.1% | **48.6%** ✅ |
> | 支配的戦略の不在 | 50% 未満・非入札 ≪ 33% | 50.4% | **46.6%** / 貯め込み ~10% ✅ |
> | 平均決着ターン | 16〜20 | 18.37 | **16.74** ✅ |
> | 終盤の単一スキル比率 | 70% 以下 | 99.5% | **49.6%** ✅ |
> | パス率 | 1〜15% | 0.8% | **1.7%** ✅ |
> | (参考)落札×勝率 相関 | ゲート外 | 0.14 | −0.20(第三席依存で符号反転) |
>
> **「落札回数と勝率の相関」は #29 でゲートから外し参考指標に再定義**した。シミュレーションにより、**過剰入札(allIn)は落札を量産しても勝率は 46.6% に留まり、落札回数と勝率はむしろ負相関**になることが判明。これは「金で確率は買えるが、金だけでは勝てない」という設計意図そのものであり、当初の「r ≥ 0.3(落札が多いほど勝つ)」前提が実態と合わない。オークションの中心性は「非入札戦略(貯め込み)が均等分 33% を大きく下回る(~10%)」= 支配的戦略 KPI に統合して担保する。

### セカンダリーKPI(利用実態 — 公開後に測定)

Cloudflare Web Analytics(Cookie 不使用・個人を特定しない集計)で測定する。

| 指標 | 目標値 | 期限 |
|---|---|---|
| 1セッションあたりの平均プレイ回数 | **1.5 回以上** | 公開後3ヶ月 |
| 初回訪問者の1戦目完了率 | **60% 以上** | 公開後3ヶ月 |
| 試合後リプレイの閲覧率 | **30% 以上** | 公開後3ヶ月 |

「平均プレイ回数 1.5 回以上」は、1戦で終わらず再戦する人が一定数いることを意味し、「読みが上達する実感」というコンセプトが機能している間接的な証拠になる。

## 機能要件

ゲームルールの詳細(数値・処理順序・エッジケース)は `docs/functional-design.md` で定義する。本書では「何ができる必要があるか」を受け入れ条件として示す。

### コア機能(MVP)

#### 1. ビンゴカード

**ユーザーストーリー**:
プレイヤーとして、自分と相手の盤面を見比べて入札額を決めるために、全員の盤面とリーチ状況が常に見える必要がある。

**受け入れ条件**:
- [ ] 数字プール 1〜40 を列ごとに区切った(B:1-8 / I:9-16 / N:17-24 / G:25-32 / O:33-40)5×5 の盤面が生成される。
- [ ] 中央(N列3行目)は FREE マスとして開始時からマーク済みで表示される。
- [ ] 3人全員の盤面が常時表示され、マーク済みのマスが視覚的に区別できる。
- [ ] リーチ(4マーク済みのライン)が盤面上で識別できる。
- [ ] 同一の乱数シードからは常に同一の盤面が生成される。

**優先度**: P0(必須)

#### 2. コイン経済

**ユーザーストーリー**:
プレイヤーとして、いま何にコインを使えるか判断するために、手持ちと予約済みの内訳が常に見える必要がある。

**受け入れ条件**:
- [ ] 各プレイヤーは初期コイン 15枚 で開始し、毎ターン開始時に 1枚 支給される。
- [ ] コインは上限 30枚 を超えて保持できず、超過分は消滅する。
- [ ] スキル選択時、そのコストが「予約」として手持ちから差し引かれ、入札に使えないことが UI 上で分かる。
- [ ] 予約したコストが**実際に徴収されるタイミングがスキルによって異なる**ことが UI 上で分かる(偏向・強奪は落札した場合のみ徴収され、落札できなければ返却される。予知は落札の有無にかかわらず即時徴収される)。
- [ ] 精算後の増減が、誰にいくら支払われたかを含めてログに残る。

**優先度**: P0(必須)

#### 3. ターン進行(同時提出 → 解決)

**ユーザーストーリー**:
プレイヤーとして、限られたコインの配分に集中するために、スキルと入札額を1つの画面で同時に決めたい。

**受け入れ条件**:
- [ ] ターゲット番号 $T$ が公開された後、スキル(偏向 / 予知 / 強奪 / なし)と入札額を1画面で提出できる。
- [ ] 提出前に「スキル代を除いた入札可能額」が表示され、それを超える入札はできない。
- [ ] 解決は「予知 → 開札 → 落札者の数字選択 → 全員のマーク → 精算 → ビンゴ判定」の順に、決定的に処理される。
- [ ] 落札者は購入した範囲から数字を1つ選ぶか、**パス**(誰にもマークさせない)を選べる。
- [ ] 同額1位の場合、優先権トークンによって決定的に落札者が決まり、トークンの位置は常時公開される。
- [ ] 提出から解決までの各処理が、後から検証できる粒度でイベントとして記録される。

**優先度**: P0(必須)

#### 4. 勝利条件と決着

**ユーザーストーリー**:
プレイヤーとして、勝敗に納得するために、どの基準で勝ったか(負けたか)が明示される必要がある。

**受け入れ条件**:
- [ ] 25ターン以内に1ライン以上のビンゴを最速で達成したプレイヤーが勝利する。
- [ ] 落札者が選んだ数字で複数人が同時に達成した場合、引き分けとして扱われる。
- [ ] 誰も達成せずに25ターンが経過した場合、「リーチラインの本数 → 総マーク数 → コイン残」の順に比較して決着し、**どの基準で決まったかが結果画面に表示される**。
- [ ] すべての基準で同値の場合は引き分けとする。

**優先度**: P0(必須)

#### 5. CPU 対戦相手(2体)

**ユーザーストーリー**:
プレイヤーとして、読み合いの手応えを得るために、行動が予測しきれないが理不尽ではない対戦相手が欲しい。

**受け入れ条件**:
- [ ] レオ / サラの2体が実装され、それぞれ異なる意思決定の傾向を持つ。
- [ ] 各 CPU の**傾向を説明する一文**が、ゲーム中いつでも参照できる位置に表示される。
- [ ] 提出前に各 CPU の状態を示す1語のテル(例:「強気」「様子見」)が表示される。テルは確率的なヒントであり確定情報ではない旨が明記される。
- [ ] CPU は**非公開情報(他者の入札・山札・他者の予知結果)を参照しない**。この事実が UI 上で明言され、実装上も `Agent` インターフェースによって構造的に保証される。
- [ ] 内部の数式・閾値はゲーム中には開示されない。

**優先度**: P0(必須)

#### 6. 試合後リプレイ

**ユーザーストーリー**:
プレイヤーとして、次の試合で勝つために、CPU が各ターンいくら入札し何を買っていたかを試合後に確認したい。

**受け入れ条件**:
- [ ] 試合終了後、全ターンの入札額・購入スキル・選択された数字・精算結果を一覧で確認できる。
- [ ] 予知で山札を操作したターンが、何を選んだかを含めて開示される。
- [ ] リプレイは同一シードから決定的に再現され、ゲーム中の表示と矛盾しない。

**優先度**: P0(必須)

#### 7. バランス検証基盤

**ユーザーストーリー**:
開発者として、ルールが成立していることを主観ではなく数値で確認するために、自動対戦でバランスを測定したい。

**受け入れ条件**:
- [ ] バランス定数(初期コイン・上限・毎ターン支給・スキル価格・分配率・ターン数・数字プール)がすべて単一の設定ファイルに外出しされ、コード中にリテラルが散らばっていない。
- [ ] シード固定の自動対戦を CLI から実行でき、**1万戦を5分以内**に完走する。
- [ ] 「成功指標(KPI)」のプライマリー指標が**7項目すべて**出力される(ビンゴ発生率 / スキル使用率 / 落札回数と勝率の相関 / 支配的戦略の不在 / 平均決着ターン / 終盤のスキル選択比率 / パス率)。
- [ ] 終盤(残り5ターン)のスキル選択比率が、スキル別に分けて出力される。予知への一極集中は Ver 3.3 で特定された既知リスクであり、これを検出できないまま P0 完了と判定してはならない。
- [ ] 複数の戦略(常に貯め込む / 常に最大入札 / スキルを買わない 等)を戦わせ、支配的戦略の有無を検証できる。

**優先度**: P0(必須)

### 将来的な機能(Post-MVP)

#### サーバー権威型への移行

ゲームロジックをそのままサーバーへ移送し、秘密入札と山札をサーバー側に閉じ込める。オンライン対戦の土台。

**優先度**: P1(重要)

#### オンライン人間対戦

マッチメイキングを実装し、空席は CPU で埋めることで3人固定のまま成立させる。

**優先度**: P2(できれば)

#### リアクションスキル

開札時にコインを払って割り込む要素。例:【関税】(落札者の支払いを +2)、【保険】(落札失敗時に入札額の半分が戻る)。

**優先度**: P2(できれば)

#### CPU キャラクターの追加

異なる傾向を持つ3体目以降の CPU。

**優先度**: P2(できれば)

#### 試合後リプレイの共有

リプレイをシードと操作列から URL で共有できるようにする。

**優先度**: P2(できれば)

## 非機能要件

### パフォーマンス

- 初回ロード: **3秒以内**に操作可能になる(4G 回線相当・キャッシュなし)。
- 提出から解決結果の表示まで: **500ms 以内**(演出時間を除く純粋な計算時間は 10ms 以内)。
- 自動対戦シミュレーション: **1万戦を5分以内**に完走する(開発機環境)。
- 配信バンドルサイズ: **gzip 200KB 以内**。

### ユーザビリティ

- 1プレイ **10〜15分**で完結する(期待ターン数 約18)。
- ビンゴのルールを知っている初見のプレイヤーが、**チュートリアルなしで1ターン目の提出を完了できる**。
- スマートフォンの縦画面(幅 375px)で、3人分の盤面と提出 UI が破綻せずに表示される。
- 各スキルの効果が、購入前に「何が選べるようになるか」として具体的に確認できる。

### 信頼性・決定性

- 同一シード・同一操作列からは**常に同一の結果**が再現される(リプレイ・シミュレーション・デバッグの前提)。
- 乱数は state 内の seed からのみ生成し、`Math.random()` を直接呼ばない。
- ルール上の全処理(分配の端数、上限超過、優先権トークン、範囲外候補の除外、同時ビンゴ)が決定的に定義され、テストで担保される。
- リロードしても進行中のゲームが失われない(ローカルへの状態保存)。

### セキュリティ

- P0 はクライアント完結のため、サーバーに送信する個人情報・認証情報を**持たない**。
- Cloudflare Pages 上で HTTPS 配信し、外部スクリプトを読み込まない。
- P1 以降のサーバー化では、**山札・開札前の他者の入札・他者が購入したスキル・他者の予知結果をクライアントへ送信しない**ことを設計制約とする。

### 保守性・拡張性

- ゲームロジックは `reduce(state, actions[]) -> { state, events[] }` の純粋関数として実装し、UI・タイマー・通信に依存しない。
- CPU は `Agent: (公開情報, 自分の秘密情報) -> Action` インターフェースで実装し、リモートプレイヤーと差し替え可能にする。
- 上記2点により、P1 のサーバー移行時にゲームロジックを書き換えないこと。

## スコープ外

明示的にスコープ外とする項目:

- **P0 でのサーバー通信・オンライン対戦**(P1/P2 で扱う。P0 はローカル完結で作り、バランスを固め切ってからサーバー化する)。
- **ユーザーアカウント・ログイン・戦績の永続化**。
- **課金・広告**。
- **3人以外の対戦人数**(オンライン時も空席を CPU で埋めることで3人固定を維持する)。
- **多言語対応**(日本語のみ)。
- **ネイティブアプリ化**。
- **ハブ(`fujioha_platform`)側の改修**。公開時に必要なゲーム登録とアイコン schema 拡張は、ハブ側リポジトリの作業として別途扱う。
